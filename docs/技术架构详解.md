## 1. 项目总览

### 1.1 定位

三星堆文化传播的数字交互展馆系统，面向答辩演示场景。核心能力：

- 首页引导 → 时空探索 → 文物展厅 → 3D 展示 → AI 讲解的完整浏览链路
- AI 虚拟导游"玄喵"：全局悬浮对话、语音输入、TTS 讲解、Agent 路由
- `/trail` 时空展线：祭祀坑地图 → 文物线索 → 3D + 图谱 → 玄喵讲解闭环
- Obsidian 第二大脑知识库：BM25 检索 + Agent RAG 问答
- Agent 智能路由：LLM 判断意图 → TOOL_CALL/RAG/DIRECT_ANSWER

### 1.2 技术栈全景

### 3.3 安全架构

```
请求 → JwtAuthenticationFilter (提取 Token)
    → SecurityContextHolder.setAuthentication()
    → JwtInterceptor (校验路径权限)
    → Controller (@PreAuthorize 或手动检查)
```

- JWT：auth0/java-jwt，HMAC256，7 天有效期
- 公开路径：登录、注册、文物分页、TTS、文件上传、Spacetime API
- 双过滤器：`JwtAuthenticationFilter`（Spring Security）+ `JwtInterceptor`（WebMvc）

## 5. AI 与 RAG 系统

### 5.1 完整对话流程

```
用户输入
    │
    ├─→① matchFixedAnswer (chatReplyConfig.js)
    │    32 个正则规则匹配高频问题
    │    匹配成功 → 直接返回预制文案 + 预制音频
    │    匹配失败 → 继续
    │
    └─→② Agent 路由 (AgentRouterService.java)
          LLM 判断意图：
          ├─→ TOOL_CALL → 调用对应工具（天气/导航/商城/展线...）
          ├─→ RAG → ③ 知识检索
          ├─→ DIRECT_ANSWER → LLM 直接回答
          └─→ UNSUPPORTED → 返回"暂不支持"
    
    ③ 知识检索 (两层)
          ├─→ 优先: KnowledgeIndexService (Obsidian Vault)
          │    GET /agent/knowledge/search?query=xxx
          │    BM25 + IDF + wikilink 关系传播
          │    ← 返回 [来源1] [来源2] ...
          │
          └─→ 降级: 前端 knowledgeSearch.js
               16 个静态 txt 文件
               同义词映射 + 双字分词打分
               ← 返回 top3 文档
    
    ④ 构建 RAG Prompt
          系统提示 + 检索资料 + 用户问题
          → 发送给 LLM
    
    ⑤ SSE 流式输出
          前端 fetchEventSource
          逐 chunk 追加到气泡
          完整后 → TTS 语音播报 + 打字机同步
```

### 5.2 知识检索评分算法

**后端 (KnowledgeIndexService)**：

```
lexicalScore = 
  + 18  (标题包含完整查询)
  + 12  (查询包含完整标题)
  + BM25 TF-IDF 分数 (termFrequency * 2.2 / (tf + 1.2) * log(1 + (N-DF+0.5)/(DF+0.5)))
  + 4.5  (标题命中查询词)
  + 2.5  (标签/关联命中查询词)
  × 1.08 (entity/concept 类型加权)

关系传播加分：
  + 源文档分数 × 0.08 → 通过 [[wikilink]] 关联的文档
```

**前端 (knowledgeSearch.js)**：

```
score = 
  + 30  (实体ID/坑位ID精确匹配)
  + 22  (同义词命中 + 语料包含规范名)
  + 14  (标题分词匹配)
  + 8   (meta 字段匹配)
  + 10  (上下文 entityId 匹配)
  + 8   (上下文标题匹配)
  + 2   (普通词命中)
```

## 6. Agent 智能路由系统

### 6.1 系统架构

```
前端 AgentOrchestrator.js
    │
    ▼ POST /agent/route

    │
    ├─ LLM 路由判断 (DeepSeek V4 Flash)
    │
```

### 7.3 索引流程

```
启动 / 定时触发 (60s)
    │
    ▼
Files.walk(knowledge-vault/wiki/)
    │ 过滤 .md 文件
    │ 路径安全检查 (防止目录穿越)
    │
    ▼ 对每个文件：
    ├── SHA-256 哈希
    ├── 与上次快照对比
    │   ├── 哈希相同 → 复用缓存文档 (reused++)
    │   └── 哈希不同 → 重新解析 (parsed++)
    │
    ▼ 解析 (KnowledgeMarkdownParser)：
    ├── Frontmatter → title, type, tags, related, sources
    ├── Markdown Body → 清洗成纯文本
    ├── Wikilink 提取 → links 集合
    ├── 中文双字分词 + 英文分词 → termFrequency
    └── 构造 KnowledgeDocument

    ▼
更新 IndexSnapshot (内存)
    ├── documentsByPath
    ├── documentsByTitle
    └── toStatus() → {indexedDocuments, lastSyncAt, durationMs}
```

### 7.4 搜索流程

```
search(query, limit=3)
    │
    ├── tokenize(query) → ["青铜", "神树", "铸造"]
    │
    ├── 计算 documentFrequency（每个词在多少文档中出现）
    │
    ├── 对每个文档计算 lexicalScore：
    │   └── BM25 TF-IDF + 标题加分 + 元数据加分 + 类型加权
    │
    ├── 关系传播加分 (addRelationshipBoosts)：
    │   └── 命中文档的 [[wikilink]] 关联文档获得 0.08 系数加分
    │
    ├── 排序取 topK
    │
    └── buildContext → 拼接成 [来源1] [来源2] ... 格式
```

## 13. 关键技术决策说明

### 13.1 为什么前端做两层知识检索？

```
第一层：后端 KnowledgeIndexService (Obsidian Vault)
  - BM25 + wikilink 关系传播
  - 增量同步、自动刷新
  - 返回结构化来源 (title/path/excerpt/score)

第二层：前端 knowledgeSearch.js (静态 txt)
  - 后端不可用时自动降级
  - 16 个 txt 文件直接 fetch
  - 同义词映射 + 双字分词打分

原因：答辩演示场景要求高可用，前端降级确保 LLM 始终有上下文
```

### 13.2 为什么不是纯向量 RAG？

```
当前实现：
  BM25 关键词匹配 + IDF 加权 + wikilink 关系传播

未使用向量数据库的原因：
  1. 知识库规模小 (38 条)，BM25 已够用
  2. 答辩演示不需要高精度语义匹配
  3. 减少外部依赖 (无需 Embedding 模型/向量库)

如果要升级：
  1. 加 Embedding 模型 (如 text-embedding-v3)
  2. 加向量数据库 (Chroma/Pgvector/Qdrant)
  3. 加语义重排序 (cross-encoder)
```

### 13.3 为什么 Agent 不做多步规划？

```
当前限制：
  单次路由 → 单次执行 → 返回结果

原因：
  1. 答辩演示场景以单轮问答为主
  2. 多步规划增加延迟和失败风险
  3. Agent 框架预留了扩展接口

如果要升级：
  1. 加 ReAct / Plan-and-Execute 模式
  2. 加中间结果缓存和状态追踪
  3. 加子任务分解和执行监控
```

### 13.4 为什么前端和前端都有 MCP？

```
后端 MCP (springboot/mcp/)：
  - 服务端工具注册表
  - 6 个数据查询工具 (商品/用户/文物等)
  - 通过 REST API 暴露

前端 MCP (vue3/src/mcp/)：
  - 客户端意图解析器
  - 20+ 工具定义 (含页面操作类)
  - 双向：可调后端 API，也可本地执行

二者互补：
  后端 MCP 提供数据查询能力
  前端 MCP 提供页面交互和意图解析
  Agent 路由层统一调度
```

### 13.5 玄喵对话链路的容错设计

```
三层兜底：
  第 1 层：固定回复白名单 (32 个正则)
    匹配高频问题 → 零延迟 + 预制音频
    完全不依赖外部服务

  第 2 层：后端知识搜索 + LLM
    KnowledgeIndexService → DeepSeek V4 Flash → SSE
    有网络时的工作链路

  第 3 层：前端本地降级
    后端 400/500 → 静态 txt 搜索 + buildFallbackReply
    LLM 不可用 → 前端本地生成简短回答
    全链路断 → "喵～我的小脑袋有点晕"
```
